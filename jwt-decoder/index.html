What is a JSON Web Token?

A JWT is a compact way to carry claims between two parties. It looks like three Base64URL strings separated by dots: header.payload.signature. The header names the signing algorithm, typically HS256 or RS256. The payload is a JSON object of claims — who the subject is, which audience the token is for, when it was issued and when it expires. The signature is computed over the first two segments using a shared secret (HMAC) or a private key (RSA/ECDSA).

Decoding is just Base64URL with padding restored. Every JWT library can do it, and so can this page: the raw bytes are decoded as UTF-8, parsed as JSON, and pretty-printed with timestamps humanized.

Claims worth checking

  • iat — issued at, seconds since the Unix epoch.
  • exp — expiry. An expired token must be rejected by the server; the badge above compares it to your clock.
  • nbf — not before: the token is invalid until this time.
  • aud — intended audience. A token for service A should not be accepted by service B.
  • iss — issuer, which the verifier must check against a trusted value.
  • sub — subject, usually a user identifier.

What decoding cannot tell you

It cannot tell you whether the token is authentic. Anyone can craft a payload and attach a random signature. Only a verifier holding the correct key can decide. It also cannot tell you whether the algorithm is safe: alg: none and algorithm-confusion attacks are real, which is why servers must pin the expected algorithm rather than trusting the header.

Frequently asked questions

Does decoding verify the signature?

No. Decoding and verification are different operations. This tool only decodes.

Why is the token in three parts?

Header, payload and signature — the last one is computed over the first two.

Is it safe to paste a production token here?

The token never leaves your browser, but a live token is a bearer credential. Use a test token when you can.
