What Base64 actually does

Base64 takes arbitrary bytes and represents every three bytes as four printable ASCII characters from a 64-character alphabet: A–Z, a–z, 0–9, + and /. Because email, JSON, XML and HTTP headers were designed for text, binary payloads are base64-encoded before they travel through them. That is why images appear as data:image/png;base64,… and why JWT segments look like random letters.

Encoding is completely reversible and requires no key. If you can decode it, so can anyone else — Base64 is transport encoding, never a security control.

Reading the padding

Each four-character group carries 24 bits. When the input length is not a multiple of three, the encoder pads the output with = characters: one byte left over produces one =, two bytes produce ==. A decoder that rejects valid strings usually trips over a stripped padding character or over a newline inserted by a mail client. This tool tolerates surrounding whitespace and missing padding, then decodes the bytes as UTF-8 so accented letters and emoji survive.

Base64 vs Base64URL

URLs and JWT headers cannot contain + or / without escaping, so the URL-safe variant swaps them for - and _ and usually drops padding. If a string contains those characters, switch to the Base64URL tool; the decoder here accepts both alphabets so you rarely have to think about it.

Common uses

  • Debugging HTTP Basic authentication headers, which are base64(user:password).
  • Reading attachment payloads from SMTP or MIME dumps.

Frequently asked questions

Is Base64 encryption?

No. It is a reversible encoding with no key. Treat decoded content as public.

Why does my Base64 fail to decode?

Check for spaces, line breaks, a truncated final group, or a URL-safe alphabet. The error line above tells you when the input is not valid Base64 at all.

Does my input leave the browser?

No. The conversion is a pure function in a JavaScript module. There is no backend to send it to.
