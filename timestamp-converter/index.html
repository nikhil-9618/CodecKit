What the Unix epoch is

Unix time counts the seconds elapsed since 00:00:00 UTC on 1 January 1970, ignoring leap seconds. It is a single integer, which makes it easy to store, sort and compare — and it is timezone-free, because the timezone only matters when you render it as text. That is why APIs, logs and databases pass timestamps as numbers and let the client decide how to display them.

Milliseconds exist because one second is coarse for modern software. JavaScript's Date.now(), Java's System.currentTimeMillis() and most event streams use milliseconds. Both are supported here: type a 10-digit value and it is read as seconds, a 13-digit value as milliseconds.

Common values

  • 0 — 1970-01-01T00:00:00Z, the epoch itself.
  • 1000000000 — 2001-09-09T01:46:40Z, the “billennium”.
  • 1700000000 — 2023-11-14T22:13:20Z, a favourite test value.
  • 2147483647 — 2038-01-19T03:14:07Z, the 32-bit signed limit behind the Year 2038 problem.
  • 253402300799 — 9999-12-31T23:59:59Z, the largest value most date libraries accept.

Seconds, milliseconds, and mistakes

Passing seconds to an API that expects milliseconds lands you in January 1970; the reverse puts you tens of thousands of years in the future. Counting the digits is the quick fix. Note that ISO 8601 strings such as 2023-11-14T22:13:20.000Z are unambiguous and human-readable — prefer them at boundaries between systems, and convert to epoch only for arithmetic.

Timestamps appear inside tokens too: JWT iat and exp claims are epoch seconds. The JWT decoder humanizes them automatically.

Frequently asked questions

Seconds or milliseconds?

Ten digits is seconds, thirteen is milliseconds. This tool detects which.

What is 0?

1970-01-01T00:00:00Z. Negative numbers are earlier dates.

Which timezone is shown?

Both UTC and your browser's local timezone.
