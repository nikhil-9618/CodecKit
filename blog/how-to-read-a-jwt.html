How to read a JWT

A JSON Web Token looks like three random strings glued together with dots. It is not random, and reading one is a five-minute skill. Here is a complete token, decoded:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNzAwMDAwMDAwLCJleHAiOjE3MDAwMDM2MDB9
.dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

Segment one: the header

Base64URL-decode it and you get {"alg":"HS256","typ":"JWT"}. The alg field names the signing algorithm — HMAC-SHA256 here, RS256 for RSA, ES256 for ECDSA. typ is optional metadata. Key IDs (kid) also live here when a server rotates keys.

The header is not trustworthy. It is part of the signed bytes, so it cannot be changed without invalidating the signature, but it is also attacker-controlled before signing: a server that selects the algorithm from this field is vulnerable to algorithm-confusion attacks. Verify with a pinned algorithm, never with whatever the token asks for.

Segment two: the payload

Decoding gives a JSON object of claims:

{
  "sub": "1234567890",
  "name": "John Doe",
  "iat": 1700000000,
  "exp": 1700003600
}

Registered claims have fixed meanings. sub identifies the principal. iat, nbf and exp are NumericDate values — seconds since the Unix epoch. aud names the intended audience and iss the issuer. Everything else is application-defined and should be treated as untrusted input even after verification: a role claim becomes a database lookup, not a string comparison against user input.

Payloads are not encrypted. Anyone holding the token can read every claim. Do not put secrets, internal hostnames or personal data in one unless you are using JWE, which encrypts the payload as well as signing it.

Segment three: the signature

For HS256, the signature is HMAC-SHA256 over the ASCII bytes of header.payload, using a shared secret, then Base64URL-encoded. For RS256 or ES256, it is a signature with the issuer's private key, checked with the matching public key. That asymmetry is why RS256 suits distributed systems: resource servers can verify without holding a signing secret.

This is the only part that carries proof. Decoding the first two segments tells you what the token claims; it tells you nothing about whether the claims are true.

The five checks that matter

  1. Signature — recompute it with the expected key and algorithm. Reject anything else.
  2. Algorithm — pin it. Reject none, and reject an RS256 token presented to an HS256 verifier (the classic confusion attack).
  3. Expiry — compare exp to the current time with a small clock-skew allowance, and honour nbf.
  4. Audience — the token must be for you. A token minted for another service should fail.
  5. Issuer — must match a known, trusted value, ideally discovered from a pinned JWKS endpoint.

Only after all five pass should you look at sub or a role claim. Skipping any of them turns a token into an assertion by the client about itself.

Reading vs verifying

Debugging needs reading: what is in this token, is it expired, which algorithm signed it. That is what a decoder does, and it is safe to do locally. Production needs verification, and that belongs on a server that holds the key. A client-side “verified” badge proves nothing because the client can lie to itself.

Common mistakes, in order of damage

  • Trusting alg from the header instead of pinning it.
  • Using the token as a session store for mutable permissions with a long expiry.
  • No revocation path: JWTs are valid until they expire unless you keep a deny-list.
  • Storing them in localStorage, where any XSS can read them. Prefer an HttpOnly, Secure, SameSite cookie.
  • Forgetting that the payload is readable, and putting something private in it.
