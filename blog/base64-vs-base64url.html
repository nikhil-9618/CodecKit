Base64 vs Base64URL

Base64 and Base64URL produce different strings for the same input, and people treat that as a quirk. It is not a quirk — it is a deliberate fix for a specific bug class: characters that mean something to the systems carrying the data.

The original alphabet is not URL-safe

Standard Base64 (RFC 4648) uses A–Z, a–z, 0–9, + and /. Those last two are the problem. In a URL path, / is a separator: a base64 blob containing a slash can become two path segments, and routers, proxies and caches will happily rewrite it. In a query string, + is decoded as a space by many form parsers, so the value changes in transit. Padding adds a third wrinkle: = is legal in a query string but awkward in filenames and some routing layers.

The URL-safe variant (RFC 4648 §5) makes three changes: + becomes -, / becomes _, and padding is usually omitted entirely. That is the whole difference. The bit stream is identical — 6 bits per character, four characters per three bytes.

Side by side

Take the bytes for the string subjects?_d, which happen to produce both special characters:

Standard:  c3ViamVjdHM/X2Q=
Base64URL: c3ViamVjdHM_X2Q

Decoding is symmetric: replace - with +, _ with /, add = until the length is a multiple of four, then run the normal decoder. Most libraries expose both as flags or separate functions; browsers give you neither, which is why every implementation carries a fifteen-line helper.

Why JWTs picked the URL-safe one

A JWT is designed to be passed in an Authorization header, a cookie, or a query parameter during an OAuth redirect. Any of those paths can mangle +, / and =. The JWS specification therefore requires Base64URL without padding for all three segments. A token that has been percent-encoded somewhere along the way is still decodable — but a token with a slash in the middle may have been truncated by a proxy long before you see it.

If you paste a token into a decoder and get “invalid input” on the signature segment, check whether some layer translated - back to + or _ to /. That usually means a base64 decoder was applied where a base64url decoder belonged.

When to use which

  • Base64 — MIME/email attachments, data URIs, PEM blocks, HTTP Basic auth. These contexts expect the standard alphabet and often expect padding.
  • Base64URL — anything that will appear in a URL, filename, cookie, or JWT/JWS/JWE segment.
  • Neither for secrets. Both are reversible by anyone; they are transport encodings, not encryption.

Padding, briefly

Base64 encodes 3 bytes into 4 characters. If the input length is not divisible by 3, the encoder emits one or two = characters to complete the final group. Padding carries no data — it exists so decoders can reject truncated strings. Base64URL drops it because the length already tells you what was missing, and because = is annoying in URLs. A tolerant decoder should accept both padded and unpadded input; ours does.
